# Decisions

| Date | Decision | Over | Because |
| --- | --- | --- | --- |
| 2026-11-01 | Real keys are saved keys with names, linked into environments; tokens are environment or service kind | A real key per service per environment, and tokens scoped to a list of services | One key used by dev and staging is rotated once, and a link switch moves every token with it. Two kinds cover what scoping lists were used for |
| 2026-11-01 | Converting revokes a token limited to two or more services, and names it in notices | Making it an environment token | An environment token would reach every service linked there, including ones linked later; failing closed means a conversion never widens what a token can do |
| 2026-11-01 | A service's ID can't be added twice; a custom service changes only through `PATCH`, and only with no saved keys for it; catalog services never change | Adding over an existing service | A service's hosts decide where its real keys are sent. `POST {"name": "OpenAI", "hosts": [...]}` used to replace the catalog's OpenAI, so anyone with an API key could point it at their own host and receive the key |
| 2026-11-01 | `tokens/ensure` hands out only tokens it made (principal `keystub-run`); unrestricted tokens from before saved keys with no principal are marked so on conversion | Handing out any live token of the name | Ensure returns the token's value; a CI job's token or a link's service token, which is named after its service, would otherwise go to whoever asks by name. Marking old ones keeps every worktree's token |
| 2026-11-01 | The CLI sends `$KEYSTUB_API_KEY` only to a server `--server` or `$KEYSTUB_SERVER` names, and sends the local admin key only after `/api/me` answers 401 as Keystub | Sending the key to whatever server resolves | A key shouldn't reach the default, `serve.json`'s server or the one `keystub login` saved, none of which it was made for. The `/api/me` check catches a stale `serve.json` (the server stopped, and something else, or nothing, on its port); it doesn't stop a program on that port that answers as Keystub on purpose, which would need a challenge only the real server can answer |
| 2026-11-01 | No downgrade after saved keys: older builds fail to start on converted data (a text `bindings` field, a `bindings` view) | Letting them run | An older build would read the data without its saved keys, then save over them |
| 2026-11-01 | Self-hosted seals each saved key once with the master key | Per-environment seals as hosted does | Self-hosted has one master key that opens everything anyway; per-environment seals would add work on every link with no boundary behind them |
| 2026-11-01 | A saved key is counted against limits only while it has one | Counting every key, as the other levels are | It keeps a write off the request path for most keys, as hosted does; usage per key comes from the request log |
| 2026-11-01 | Self-hosted's admin API key is `admin.token`; the CLI reads it only for the server on the same machine (the dashboard address in `serve.json`), never sends it elsewhere | A separate API key to create, or device login on self-hosted | The file already exists (0600) and already is the admin's credential; anyone who can read it can already use the dashboard. A key minted from a file would be the same power with more steps. Matching the server exactly keeps it from leaking to another `--server`. A dashboard bound to one of this machine's own addresses (a LAN IP) works too, over plain http, since that never leaves the machine |
| 2026-11-01 | CLI server: `--server`, `$KEYSTUB_SERVER`, the server `keystub login` used, the local `keystub serve`, then `https://app.keystub.app`. Credential: `$KEYSTUB_API_KEY` (only with `--server` or `$KEYSTUB_SERVER`), the login token for that same server, then the local admin key | Prompting, or one fixed default | Agents and CI set variables; people log in once; on a box with `keystub serve` the CLI works with no setup. A credential is only ever sent to the server it was made for |
| 2026-11-01 | CLI exit codes 0 ok, 1 error, 2 usage, 3 not signed in, 4 not found, 5 conflict; `--json` errors on stdout with `exitCode`; no prompts when stdin isn't a terminal | Exit 1 for everything | Agents branch on the code without parsing text. A prompt with no terminal would hang them, so deletes need `--yes` there |
| 2026-11-01 | A key's value reaches the CLI on stdin, from `--from-env`, or typed hidden; never as an argument; a new token is printed once, alone on stdout (`token` under `--json`) | `--value KEY` | Arguments show in `ps` and shell history. Printing only the token on stdout lets `$(keystub tokens create …)` capture it |
| 2026-11-01 | The agent guide lives in `docs/llms.txt`, printed by `keystub help agents` | Text in the CLI's code | One file to keep current, which the hosted side can publish as `llms.txt` |
| 2026-10-31 | Renamed from Stubkey to Keystub (keystub.app); proxy tokens keep the `sk-stub-` format, and old names still work: `STUBKEY_*` variables, `~/.stubkey`, `stubkey.db`, the old Keychain items (moved on first use) and the `Stubkey-Token` header | A clean break | The domain; and every token already handed out, every `.envrc` and every linked machine keeps working |
| 2026-10-31 | The admin types the machine's code, sees that request's name, address and time, then approves it | Clicking Approve on a list of waiting machines, or approving on the code alone | Anyone who can reach the edge can ask to be linked under any name; typing the code shown on the real machine, and seeing what it belongs to, means a look-alike or phished request isn't approved by mistake (as RFC 8628 suggests) |
| 2026-10-31 | A machine may use the environments ticked at approval | Every environment, or tokens scoped per machine | A laptop linked for dev shouldn't get prod keys by asking; services stay unscoped, so `keystub run` works for the whole environment |
| 2026-10-31 | Machine link requests live in memory for 10 minutes, at most 10,000, 3 from one source (IPv4 address or IPv6 /64) and 10 from one network (/24 or /48); a reverse proxy's header only when trusted | Storing them | They're short-lived, and a restart only means running `keystub link` again. The caps bound memory and keep one source from filling the list; a turned-down request frees its slot at once |
| 2026-10-31 | A revoked machine's tokens are refused wherever tokens are used | Relying on marking each token revoked | Revoking marks them one by one; if saving one fails, the machine's check still stops it, so revocation never half-applies |
| 2026-10-31 | Machine tokens last 30 days | No lifetime | A machine's credential is readable by anything running as its user; tokens that expire limit what a copied one is worth. `keystub run` makes a fresh one as needed |
| 2026-10-31 | An agent learns which hosts to decrypt from the edge's `GET /catalog`, asked with a proxy token | Decrypting every host in the embedded catalog | Decrypting a host the edge doesn't serve (no key in the token's environment) would break the box's own credentials for it |
| 2026-10-31 | Of the edge's hosts, an agent decrypts only those the built-in catalog gives that service, or allowed on the box (`--allow-host HOST` for custom services, `SERVICE=HOST` for a built-in's own server) | Trusting every host the edge names; letting an allowed host be any service's | The edge is a trust boundary: a compromised one, or a tenant admin's custom service, could otherwise name `github.com` or an internal host and get every box's traffic for it, cookies and credentials included. If the edge could file an allowed host under a built-in service, it could set `GH_TOKEN` to a token `gh` sends to github.com |
| 2026-10-31 | In forwarding mode, an auth header holding a real credential is refused on the box (400) | Forwarding it for the edge to overwrite | The box's own credentials in auth headers never reaching the edge is the agent's promise; under `keystub run` every request carries a token, so the "no token" check alone doesn't keep it |
| 2026-10-31 | A built-in service's header and variables come from the built-in catalog; a custom one may set only key-named variables no built-in service reads, and no base URL; a built-in host is decrypted only as its own service | Taking the server's catalog as it is | A server that names variables can set `BASH_ENV` or `GIT_SSH_COMMAND`, or point `PIP_INDEX_URL` at itself, and run code on every box; one that names the header can stop the box from noticing a real key in it. Setting `GITHUB_TOKEN` would send the proxy token to GitHub and stop `gh` working; a custom service under an allowed `*.googleapis.com` would otherwise take Gemini's host with its own header, and the box's real `x-goog-api-key` would reach the edge |
| 2026-10-31 | `keystub run --remote` starts a private agent for the one command | Requiring a running `keystub agent` | A sandbox or CI job has a token and one command; one line with no daemon is what it can use |
| 2026-10-31 | The agent listens on loopback only | A shared agent | It can't check tokens itself, so anyone who reached it could use it with any token they hold; a shared proxy is `keystub serve` |
| 2026-10-31 | Swap the token only in `Authorization` and the service's own header; refuse a token anywhere else | Swapping wherever it appears, or in a list of generic API-key headers | A service may store or echo any header it doesn't treat as a credential (Stripe returns idempotency keys on events; an unknown `X-Token` may be kept), which would hand the real key back to the box |
| 2026-10-31 | Users don't name the auth header for a service | A required header per service | The catalog names it for known services; custom ones default to `Authorization`, and only the rare service that uses another header needs it named |
| 2026-10-31 | Self-hosted serves the same `/s` and `/h` routes as hosted | Self-hosted as the local proxy only | Every mode then works self-hosted, and the agent and quick-start config differ only in the URL |
| 2026-10-31 | Open core: everything customers run is open source; the hosted platform is closed | Open sourcing the hosted platform | Customers can audit what runs on their machines; the hosted service stays the business |
| 2026-10-31 | Hosted limits in Durable Objects | KV counters | KV is eventually consistent, allows about one write per second per key and has no atomic increment, so counts would be lost |
| 2026-10-31 | Hosted edge on Cloudflare Workers | Go on Fly | A few ms of overhead near most users and APIs, no servers to run; Workers can't accept `CONNECT`, so TLS decryption stays in Go |
| 2026-10-31 | Flat proxy tokens | A parent/child token tree | Delegation without admin access is a niche need; expiring, scoped tokens cover sandboxes and CI |
| 2026-10-31 | A refused request counts against no limit | Counting at check time | A missing or unreadable key, or a full limit at another level, shouldn't use up a token's quota |
| 2026-10-30 | Built from scratch in Go, with ports and adapters | Building on iron-proxy | Full control over the request path, and every hosting-specific part can be swapped |
| 2026-10-30 | Master key per platform: Keychain on a Mac, env var on servers, file as a last resort | One file everywhere | Keys at rest stay protected by what each platform already trusts |
